## Rulings

**R1. Under-18 suspension needs corroboration (B-C1, C-I2, J1). Amend 0005.**
- Qualification keeps R4's conditions with one change. An `interaction` row written **by the reporter** counts only
  for `like` and `pass`, which the served rule already checks. The reporter's own `request` interaction rows never
  count. Rows written by the target, `connection_requests`, matches and messages count as before.
- **Suspension (hide)** happens only when:
  - **(a)** at least 2 distinct qualifying reporters filed `underage` reports within 30 days; or
  - **(b)** one qualifying `underage` report comes from a reporter who has a **match** with the target. A match needs
    the target's own consent, so one person cannot manufacture it.
- **A single non-corroborated `underage` report** is stored and qualifying. It raises a founder alert (R5) and enters
  the 72 h review queue (new `member_report.reviewed_at`). It **does not hide** the target.
- *Why:* the threat is one actor taking an adult offline. Two independent reporters, or a mutual match, is the
  cheapest rule that defeats a single sock. It still lets a real chat partner act alone.
- The cost is that a genuine minor seen only in the deck stays visible until review. The alert and the 72 h queue
  bound that window.
- privacy.html:94 and 155 change to describe the new rule.

**R2. A mutual relation is not required for qualification in general.** It is required only for the single-report
suspension path (R1b). C's broader rule would make almost every deck-only report of a fake or spam account
non-qualifying, and the `reported` density flag would never fire. The dissent is preserved below.

**R3. The enforcement ladder gets a real top rung (B-I1). Amend 0005.**
- **`banned`**: a new flag reason.
  - `brivia_member_completed` excludes it, so the member is hidden both ways and cannot message.
  - It never expires and no automatic upsert replaces it.
- **The `restricted` statement** in MODERATION.md must not replace `suspended_pending_review` or `banned`: add
  `where reason not in (…)`.
- **One owner-only operator helper**, `moderation_remove_member(uuid, reason)`. It writes the tombstone and the
  `account_deleted` consent event, then deletes `auth.users`. It serves three needs:
  - a confirmed minor;
  - a banned harasser, after the founder preserves evidence;
  - the DPDP s.12 fallback when self-serve deletion fails (R6).
- **Rejoin:** when a live tombstone's reasons include `underage` or `banned`, `declare_adult` writes
  `suspended_pending_review` (hidden, and it alerts) instead of `rejoin_review`.
- **Tombstone scope (C-I3):** a tombstone is written only for qualifying reports or flags, and its reasons come only
  from those.
- **Gmail-dot and plus-alias normalisation is P2.** A new address defeats the digest anyway. MODERATION.md states this
  limit.

**R4. Evidence preservation on deletion (B-C2): hold, not destroy. Amend 0005.** *[counsel]*
- **Where the check runs:** in `delete_my_account`, after the `amr` check and **before** the storage check.
- **When it triggers:** the caller has any `member_flag`, or is the target of a qualifying report from the last 30 days
  whose `reviewed_at` is null.
- **What the RPC does then:**
  - it raises P0001 `deletion_held` and records the request in a new owner-only `deletion_request(member_id,
    requested_at)` table;
  - it deletes nothing.
- **Why storage survives:** the client empties storage only on `storage_not_empty` (F1), so the files stay in place.
- **Founder duty:** the founder completes each held deletion with `moderation_remove_member` within 30 days. Before
  that, the founder copies any attachment that is needed as evidence.
- **Client copy:** "Your account is being reviewed, so we can't delete it straight away. We've recorded your request
  and will delete it within 30 days."
- **Deletion before any report** (the victim had not yet reported) stays a disclosed limit. The question for counsel
  is P1: should messages a deleting member sent stay visible to recipients for a short window?

**R5. Founder alerting: a webhook with counts only.**
- **Why a webhook:** a dashboard query or a summary row is still something the founder must remember to pull, and the
  72 h promise needs a push. There is no email infrastructure.
- **What to build:** a new `0007_moderation_alert.sql`. It is separate because it depends on `pg_net`, a new live
  extension, and it is isolated the same way 0006 was.
- **The job:** pg_cron runs hourly.
  - It writes one `moderation_digest` row each run. That row is the pull fallback and is read in MODERATION.md step 0.
  - It calls `net.http_post` to a founder-owned webhook (ntfy, Discord or Slack) whose URL sits in an owner-only config
    table. If no URL is configured, it does nothing.
- **When it posts:** only when at least one of these is true:
  - a new `underage` report;
  - an `underage` report or a suspension older than 48 h that has not been reviewed;
  - a new `deletion_request`;
  - a failed `purge_expired_requests` run in `cron.job_run_details` in the last 26 h.
- **Payload:** counts plus "open MODERATION.md". It carries **no ids, names or text**, so the third-party webhook
  receives no personal data.
- **The promise:** privacy.html softens to "We aim to review… within 72 hours". MODERATION.md gains a vacation-cover
  step.

**R6. Live rehearsal before any real member (B-I2, C-I6).**
- **Order:** right after 0005 and the client are live, run the README read-only checks, then delete a throwaway
  **test-world** member on live in two ways:
  - by password re-auth;
  - by the Google re-auth round trip.
- **What to verify:** `auth.jwt()->'amr'` has the expected shape, and no row remains in `auth.identities`,
  `auth.sessions` or any public FK table.
- **If it fails:** the deletion UI shows the email fallback, and the founder uses `moderation_remove_member` until it
  is fixed.

**R7. Under-review access (A-C1).** The under-review card adds a Privacy & account action and a privacy-notice link.
- Withdrawal works immediately.
- Delete always takes the R4 hold path, because a suspended member has a flag. So A-C1 is closed without reopening
  B-C2.

**R8. Collapse the duplicates in 0005 before the first apply (C-I5).** Each function gets one final definition. The
README gains a "0004 bodies replaced by 0005" table. This is a pure edit, and the harness plus the drift test re-prove
it.

**R9. Purge robustness (C-I4): fail loud, do not wrap.**
- Retention is all-or-nothing by design. Wrapping deletes in exception blocks would turn a silent rollback into a
  silent partial purge.
- Failure detection comes from R5's `cron.job_run_details` check.
- *P1:* split the purge into two cron jobs (retention, then requests) only if a failure is ever observed.

**R10. Honesty (A-I3, B-I3): P0-C copy, shipped with the 0005 client.** Make these changes:
- Strike privacy.html:49 "nothing… does not need".
- Replace "as easy as giving it" with "at any time; it takes effect at once".
- Reporter line: "with your name removed; your note and the quoted messages may still identify you."
- Access: "we reply within 30 days" *[founder confirm]*.
- Rewrite the under-18 sentences to match R1.
- Fix the `app.js:1577` helper.
- Add career data to "What remains" (or state it as a separate purpose).
- Rejected: the public-attachment disclosure (the bucket is private).

**R11. Auth hardening is a founder gate (row 7), and it comes before R1's value is real.** Corroboration is only as
strong as the cost of a sock.

### Critic B (privacy, security, abuse, DPDP) on iteration 4, snapshot c208bdc

Method: static read of 0005 in full, 0001/0003/0004 lines it depends on, privacy.html, MODERATION.md, account-deletion.js. I did not run the harness or any probe. #### Critical

**C1. One tap makes a sock puppet a "qualifying" reporter, and one qualifying under-18 report hides an adult from everyone.**
- `like`/`pass` rows need only a deck impression in the last 7 days (0004:1598-1618). `report_member` counts any non-impression interaction as a relation (0005:403-405).
- So the gate is: an account at least 7 days old, completed, with one like on the target. That is cheap while email confirmation is off (gate row 7).
- `reason='underage'` by one qualifying reporter inserts `suspended_pending_review` (0005:438-443). This is invisible to everyone, blocks messaging (0001:218-222 needs completion) and never expires.
- The cap is 10 reports a day per account, with no cross-account limit per target.
- Restoring the adult depends on the founder reading a SQL query daily. Nothing alerts (MODERATION.md:3-4). The 72 h promise in privacy.html is therefore unenforced.
- The victim sees only "being reviewed" and has no appeal beyond email.
- A competitor or ex-partner can take a real member offline in one action.
- **Fix:** an underage report suspends only with corroboration (2 distinct qualifying reporters, or one reporter plus a mutual match or at least 3 messages from the target). Otherwise it queues for review without hiding. Also add a founder alert (see P0-3).

**C2. A harasser can destroy the victim's evidence by deleting their account.**
- `delete_my_account` cascades all messages on both sides (0001:195-196). The client first removes the deleter's attachments (account-deletion.js).
- A victim who has not yet reported can never report: `report_member` returns silently for an unknown target (0005:393).
- Evidence is captured only at report time. For explicit or child-safety content, India's reporting duties (POCSO, IT Rules) make unpreserved deletion a counsel question.
- The tombstone survives only if a report or flag already exists.
- **Fix:** do not purge messages and attachments immediately when the member has an open report. Also give the recipient a short evidence-preserve window (for example 7 days), on counsel advice.

#### Important

**I1. The moderation ladder has one real action.**
- `reported`, `restricted` and `rejoin_review` only drop a member from density (MODERATION.md table; 0004:938).
- `restricted`, "confirmed abuse", leaves the member fully visible and able to message. Using it on a suspended member un-hides them (MODERATION.md §5).
- There is no ban, no hide-without-suspend and no operator delete statement for a confirmed under-18 or harasser.
- Rejoin of a confirmed minor produces `rejoin_review`, which does not hide them (0005:509). They are visible at once. The evasion defence is review-only, and the founder reads it daily at best.
- The digest is the exact lower-cased email (0005:476). Gmail dots, plus-aliases and Google OAuth with a different address all bypass it.
- **Fix:** `rejoin_review` hides when the tombstone reasons include `underage`. Add a `banned` flag that hides and blocks. Normalise Gmail aliases in the digest.

**I2. Deletion depends on an unverified live assumption.**
- The `amr[].timestamp` shape is still unchecked on live (packet). If it is wrong, every deletion returns `reauth_required` (0005:563-565), which would block erasure. Nothing then works except the email fallback.
- `delete from auth.users` by the definer role has not been run against the live Supabase privileges. It exists only in a harness stub.

**I3. The notice is honest in most places but over-claims in four.**
- "Reports you made are kept without your name" (privacy.html "What remains"). But `member_report.note` and `evidence` hold the reporter's own words and message bodies (0005:345-352), which can identify them. Disclose it, or redact.
- "Access: ask us" is manual and has no export tool or owner. The grievance officer is "the founder" with no name.
- The 18+ block describes a self-declaration as the age check. A bare checkbox may not meet the DPDP children's-data standard of "verifiable" consent. This is a counsel item, and a person who falsely ticks stays in until reported.
- Career resumes and applications persist after a self-deletion (not in "What remains"). Their cleanup is a monthly manual SQL step (MODERATION.md §6).

**I4. Sock-farm and report spam are cheap.** `member_report` and `evidence` hold up to 50 messages per row, 10 rows per account per day. The founder can then no longer tell that a sock ring filed false reports.

### Critic C (data integrity, operations, ORBIT and IP), iteration 4, c208bdc

Method: read 0005 in full, the harness runner, the stub, MODERATION.md, privacy.html retention rows and ORBIT_ENGINE.md sections 7, 9.1.6 and 10. I ran nothing against the harness or any database.

#### Critical
None. 0005 is internally consistent and the spec matches the code on every retention and consent rule I checked.

#### Important

**I1. The 72-hour promise rests on a manual daily SQL routine with no alert.** docs/MODERATION.md:1-8 says "Nothing alerts you to a new report". privacy.html promises that every under-18 report is reviewed within 72 hours. One qualifying report hides an adult from everyone (0005:`brivia_member_completed` suspension clause, ~line 170). A solo founder who is ill for 3 days breaks a written promise and leaves an adult hidden. This is the main operating risk of the design. Fix before real members, not after (see P0-1).

**I2. One report can suspend any adult.** A report qualifies on any `interaction` row whose event is not `impression` (0005:~392). That includes the reporter's own `like` or `pass`. A like is only allowed on a target the deck showed in the last 7 days (spec 9.1.6), so any completed account older than 7 days can pass on anyone and then qualify. One `underage` report then sets `suspended_pending_review` with no expiry (0005:~428). Only the founder can lift it. Reporters are capped at 10 per 24 h, but sybils multiply that. A related abuse: flagged members drop out of the k-anonymity count (0004:938), so two sybil reporters can lower a cell's density.
- The relation used for qualification should be a mutual one: an accepted match, a request in either direction, or a message from the target.
- A like or pass by the reporter alone should not count.
- This needs a ruling, because R4 chose the current rule.

**I3. A tombstone is written after any report, including a non-qualifying one.** 0005:~575 tests `cardinality(v_reports) > 0`, and `report_member` stores non-qualifying reports. A griefer reports a victim from a fresh account. If the victim ever deletes and rejoins, they get `rejoin_review` and drop out of the k-count. The effect is small, but it contradicts the "flagged or reported" framing in privacy.html:115. Count only qualifying reports, or flags.

**I4. Retention is one transaction, with no monitoring.** `purge_expired_requests` (0005:~598-628) is one function holding 13 deletes. One failure rolls back all of them, and retention stops without any signal. The stub has no `cron` schema, so the `cron.job_run_details` branch (line 620) is never executed by the harness. The live-only paths are therefore untested: the `postgres` role's delete rights on that table, and the schema's existence on Supabase. The documented routine does not check "did last night's purge succeed". Add a last-success marker and a check line in MODERATION.md. Wrap the cron cleanup in an exception block so it cannot block the data purge.

**I5. 0005 is 649 lines. It redefines frozen 0004 bodies and also redefines its own functions.**
- Frozen 0004 bodies redefined: `brivia_member_completed`, `brivia_profiles_consent_on_insert`, `purge_expired_requests`, `my_onboarding_status`, `set_sensitive_consent`.

- Collapse each function to a single final definition before applying to live. This is a pure edit, and the harness re-proves it.
- Keep a 0004-to-0005 "functions replaced" table in the migrations README so a future 0007 knows the lineage.

**I6. Stub fidelity gaps that matter on the first live run.**
